# Ome Music 产品整改建议书与执行计划

## 1. 文档目的

本计划用于收口当前版本中已经确认的产品完整性问题。目标不是继续增加功能，而是恢复一个音乐播放器最基本的可信度：窗口稳定、设置由用户掌控、关闭的音乐源不会被访问、登录流程真实可用、网易云服务不会随机掉线。

在本计划全部通过前：

- 冻结合并 PR #15。
- 不创建新版本标签，不发布 v0.4.0。
- 不以 `npm run build`、CI 绿色或界面截图代替真实产品验收。
- 不修改或清理用户音乐、数据库、缓存、登录会话和凭据。

## 2. 产品原则

1. **用户控制优先**：软件不得静默启用来源、覆盖无关设置或自行打开设置页。
2. **音乐源可靠性优先**：先保证本地音乐和网易云稳定，再扩展 QQ 音乐登录能力。
3. **明确失败优先**：无法登录、搜索或播放时，必须说明原因，不能静默失败或假装成功。
4. **轻量优先**：不为了修复引入大型依赖、本地模型或多余后台服务。
5. **真实验收优先**：自动检查、桌面端交互和人工验收缺一不可。

## 3. 已确认问题与处置建议

| 等级 | 问题 | 用户影响 | 建议 |
| --- | --- | --- | --- |
| P0 | 全局保存会同时写回多个异步加载的音源草稿 | 未操作的音源可能被覆盖或重新启用 | 拆分保存边界；每个模块只写自己的字段 |
| P0 | 搜索使用过期的音源开关状态 | 已关闭来源仍可能发起请求或显示入口 | 建立单一配置快照；关闭即零请求、零结果 |
| P0 | 1040px 最小窗口装不下当前双列布局 | 窗口化裁切、重叠、观感失控 | 在 1180px 左右进入紧凑布局并完成尺寸矩阵验收 |
| P0 | QQ 音乐只有 QQ Connect 扫码 | 微信扫码缺失，产品承诺不完整 | 明确提供 QQ / 微信两种登录方式 |
| P0 | QQ 网页凭据提取链路可能截断且经过前端 | 登录不稳定，并扩大凭据暴露面 | 提取、校验、保存全部在 Rust 内一次完成 |
| P0 | 网易云本地服务存在并发启动竞争 | 重复进程、端口冲突、偶发掉线 | 改为单实例启动状态机和共享就绪任务 |
| P1 | 外部浏览器登录提示可以“检测登录” | 实际无法读取系统浏览器会话，流程误导 | 移除误导入口，改用嵌入式官方登录或手动导入 |
| P1 | 关闭来源仍显示搜索分组和 Enable 按钮 | 容易误触设置，破坏来源隔离感 | 搜索中隐藏关闭来源，只保留固定设置入口 |
| P1 | 网易云无配置记录时默认开启 | 新用户未明确同意便进入来源准备流程 | 首次默认关闭，由引导明确启用 |
| P1 | 当前回归测试主要是源码正则检查 | CI 通过但真实流程仍可失败 | 增加行为测试、桌面尺寸测试和人工发布门禁 |

## 4. 分阶段执行计划

### 阶段 0：冻结与基线

**目标**：在修复前保存可比较、可回滚的基线。

执行项：

1. 保持 PR #15 未合并，暂停 Release 工作流和版本标签。
2. 记录当前 commit、工作区既有修改和四档窗口截图。
3. 建立脱敏测试账号/模拟凭据，不使用真实 Cookie 进入自动化日志。
4. 记录三个音源当前启用状态，作为设置不被篡改的基准快照。

**验收标准**：

- 基线报告包含 commit、版本、构建结果和已知问题。
- 不读取、不输出真实 Cookie、Token、手机号或 API Key。
- 修复分支与用户现有修改边界清楚，可逐阶段回滚。

### 阶段 1：设置所有权与音源隔离

**目标**：任何音源状态变化都只能来自用户对该音源的明确操作。

执行项：

1. 移除“一次保存全部来源”的行为；鉴赏家、网易云、Bilibili、QQ 音乐分别保存。
2. 配置加载完成前禁用对应保存按钮。
3. 登录成功只更新当前来源的登录态；是否启用来源由明确操作或带确认的登录事务决定。
4. 建立统一的音源配置快照与变更事件，搜索框不再自行维护三份可能过期的状态。
5. 搜索开始时捕获启用来源快照；配置变化时取消旧请求。
6. 关闭来源不渲染结果分组，不启动后台服务，不提供搜索面板内的 Enable 按钮。
7. 设置页只能由明确的点击或键盘操作打开，禁止 effect、失败回调或搜索请求自行打开。

**验收标准**：

- 只修改 QQ 音乐后，网易云和 Bilibili 的配置逐字段完全不变。
- 只修改鉴赏家设置后，三个音乐源配置逐字段完全不变。
- 仅启用 QQ 音乐搜索同一关键词时，网易云和 Bilibili 请求数均为 0。
- 搜索过程中关闭来源，未完成请求被取消，旧结果立即清空。
- 连续搜索、播放失败和登录失败均不会自动打开设置页。
- 重启应用后，各来源启用状态与关闭前一致。

### 阶段 2：窗口化布局修复

**目标**：窗口化与全屏使用同一套稳定、沉浸的视觉层级。

执行项：

1. 重新计算主舞台的列宽、间距、内边距和标题栏占用。
2. 在约 1180px 以下进入紧凑双列或单列模式，不再依赖 768px 断点。
3. 移除会掩盖布局错误的无条件裁切；背景层可隐藏，内容层必须可达。
4. 限制封面、歌词字号和控制栏尺寸，使其随容器档位变化而非随视口无限挤压。
5. 检查搜索、设置、队列和 DJ Dock 在小窗口中的滚动所有权。

**验收标准**：

- `1040x640`、`1180x680`、`1280x720`、`1440x900` 和全屏均无重叠、裁切或横向滚动。
- 最小窗口下封面、标题、播放控制和窗口按钮全部可操作。
- 搜索结果、设置页和队列分别只有一个明确的纵向滚动容器。
- 最大化、还原至少连续执行 10 次，布局不跳动、不留下空白区域。
- Playwright 截图差异经过人工确认，Console 无布局相关错误。

### 阶段 3：QQ 音乐登录收口

**目标**：QQ 扫码、微信扫码、嵌入式网页登录和手动导入都具有明确且真实的结果。

执行项：

1. 登录模式明确拆分为 `QQ 扫码` 与 `微信扫码`，界面清楚标识当前模式。
2. 优先使用 QQ 音乐官方登录页面承载微信登录，不复制或伪造第三方登录页面。
3. 移除“外部浏览器登录后点击检测即可导入”的误导流程。
4. 将 WebView Cookie 提取、可信域校验、会话验证和安全保存合并为单个 Rust command。
5. Windows 下使用 WebView2 CookieManager；删除 `document.title` 和本地 TCP beacon 传递凭据的回退路径。
6. 手动导入改为可滚动多行输入，粘贴后只显示长度/掩码，不回显完整内容。
7. 会话验证失败时不保存凭据、不自动启用来源，并给出可理解的原因。

**验收标准**：

- QQ 扫码和微信扫码各连续完成 3 次登录，状态均能在重启后恢复。
- 登录取消、二维码过期、网络断开均不会留下“已登录”的假状态。
- 使用大于 16KB 的虚拟凭据进行导入测试，数据不截断；真实凭据不进入前端 state、URL、标题或日志。
- 外部非 QQ 音乐域名无法触发凭据提取。
- 登录失败不会改变网易云、Bilibili 或本地音乐配置。
- 退出登录后凭据被移除，但其他来源和本地音乐不受影响。

### 阶段 4：网易云服务与会话稳定性

**目标**：服务启动、登录会话和播放请求彼此解耦，消除偶发掉线。

执行项：

1. 使用单实例启动状态机管理 `stopped / starting / ready / failed`。
2. 并发调用共享同一个启动任务，不重复创建 Node 子进程。
3. 健康检查除 HTTP 状态外验证服务身份或版本，避免误认占用端口的其他程序。
4. 搜索和播放等待共享就绪状态，不在轮询中重复调用启动命令。
5. 子进程退出后按有限退避策略恢复，并向 UI 返回稳定的失败原因。
6. 登录会话独立保存；服务重启不得清空 Cookie 或把未知状态误报为登出。
7. 首次无配置时默认关闭网易云，由引导页明确启用。

**验收标准**：

- 20 个并发 `ensure` 请求最多创建 1 个受管进程。
- 连续启动/关闭应用 10 次，不出现残留 Node 进程或黑色终端窗口。
- 模拟端口占用时不会把无关服务判断为网易云 API，并显示明确提示。
- 登录后重启受管服务，登录态和会员可播权限保持不变。
- 连续搜索 30 次、切歌 30 次，不出现随机服务掉线或重复启动。
- Cookie 过期与服务不可用被区分为不同状态和提示。

### 阶段 5：真实测试体系与发布门禁

**目标**：让 CI 证明行为，而不只是证明代码中存在某些字符串。

执行项：

1. 保留现有静态回归检查，但将其降级为安全护栏。
2. 为设置 reducer/存储边界增加单元测试。
3. 为搜索来源隔离增加带请求计数的 provider 集成测试。
4. 为网易云服务状态机增加并发与端口冲突测试。
5. 使用 Playwright/Tauri 驱动完成窗口矩阵、设置、搜索和浮层回归。
6. 发布前执行一次真实 Windows 安装包人工验收。

**验收标准**：

- TypeScript、ESLint、Prettier、Vite build、Rust fmt、Clippy、Cargo check 全部通过。
- 新增测试至少覆盖：设置不串写、关闭来源零请求、并发单实例、窗口最小尺寸。
- Playwright 无 Console error、无页面横向溢出、无重复滚动条。
- Windows 安装、首次启动、重启、卸载后保留/清理行为符合文档。
- 所有 P0 测试连续通过 3 轮，且没有通过重试掩盖失败。

## 5. 总体验收矩阵

| 场景 | 必须结果 |
| --- | --- |
| 仅启用本地音乐 | 不访问任何外部音乐源 |
| 仅启用 QQ 音乐 | 只出现 QQ 结果，只产生 QQ 请求 |
| 仅启用网易云 | 只出现网易云结果，服务只启动一次 |
| 全部来源关闭 | 只搜索本地曲库，不打开设置，不弹环境提示 |
| 设置页只保存一个模块 | 其他模块数据库值和凭据状态完全不变 |
| QQ/微信扫码过期 | 保持登出，允许重新生成，不保存半成品凭据 |
| 网易云服务重启 | 登录状态保留，播放恢复或给出明确原因 |
| 1040x640 窗口 | 主信息和控制完整可见，无裁切与重叠 |
| 全屏与还原 | 状态、进度、浮层位置和滚动位置保持稳定 |

## 6. 发布完成定义

只有同时满足以下条件，版本才可称为 Release Candidate：

1. 所有 P0 问题关闭并有可重复测试。
2. 所有自动检查通过。
3. 四档窗口截图与桌面交互人工验收通过。
4. 三种音乐来源分别完成启用、搜索、播放、关闭、重启验证。
5. QQ 与微信登录流程均完成真实验收，或在版本说明中明确移除未完成入口。
6. 网易云登录、会员播放、服务重启连续通过三轮。
7. 设置快照证明软件未修改用户未操作的配置。
8. Windows NSIS 安装包在干净环境中安装并启动成功。
9. PR 审查结论为可合并，CI 绿色，维护文档和变更日志同步更新。

任一 P0 未满足时，不允许合并、打标签或发布。

## 7. 风险、回滚与范围控制

- 每个阶段单独提交，禁止把 UI、认证和服务状态机混成一个不可回滚提交。
- 不新增依赖，除非现有 Tauri、WebView2、React 与 Rust 能力无法完成，并先评估体积与隐私成本。
- 不迁移或删除数据库；若必须变更 schema，应另行审批并提供备份/回滚方案。
- 不打印真实凭据；测试使用虚拟长字符串和脱敏账号。
- 阶段验收失败时只回滚该阶段，不用 `git reset --hard` 或强制推送覆盖用户工作。

## 8. 推荐实施顺序

`阶段 0 基线` → `阶段 1 设置与隔离` → `阶段 2 窗口` → `阶段 3 QQ 登录` → `阶段 4 网易云稳定性` → `阶段 5 测试与发布门禁`

优先级不能调换。设置所有权和来源隔离未修好之前，不应继续扩展登录入口；网易云稳定性未通过之前，不应进入发布工作。
